# スタブ可否の判定仕様(草案)

判定ロジックとテストはこの文書を基準にする。実装の都合で決めた規則は、ここのどの項に当たるかを示せること。

## 1. 守るべき性質

パッケージ P をスタブ S に置き換えた(または除外した)プログラムが、**エントリーポイントから到達しうる全ての実行で、元と同じ観測結果(出力・戻り値・例外・ファイル)になる**こと。

- 「stubbable / nofollow / サブモジュールのヒント」を出してよいのは、この性質を静的に示せたときだけ。
- 示せないとき(解析不能・判断に迷う)は required。
- 逆方向(示せるのに required)は安全だが削減の取りこぼしであり、不具合として数える。

## 2. 操作の分類

P 由来のオブジェクトに対する操作を 3 種に分ける。

| 分類 | 操作 | 扱い |
|---|---|---|
| A. 束縛 | `import P`、`from P import x`、`P.x` の読み出し、別名への代入、型注釈 | スタブが同じ名前を同じ種類(クラス / 関数 / 定数 / サブモジュール)で提供すれば安全 |
| B. 判別 | `isinstance(v, P.C)`、`issubclass`、`except P.Err`、`v is P.X`、`hasattr(P, "x")`、`P is None` | 結果が元と同じになる場合に限り安全。下の 3 節 |
| C. 実行 | 呼び出し、インスタンス化、継承、デコレータ適用、演算、反復、`with`、値として外へ渡す | P の実装が要る。到達可能なら required |

定義時に評価されるもの(既定引数、デコレータ、クラス本体、モジュール直下の式)は、その定義が置かれた場所の実行として数える。

## 3. 判別(B)が安全な条件

- `isinstance(v, P.C)` / `except P.Err`: P の実体がどこでも生成されない(C の到達可能な実行が無い)なら、元でもスタブでも結果は偽で一致する。スタブの C はクラス、Err は元と同じ基底(`Exception` 等)を継ぐこと。
- **有無の検出**(`try: import P / except ImportError`、`hasattr`、`P is None`、`find_spec("P")`): 元の環境では P が「ある」。
  - スタブに置き換える場合: 「ある」側の分岐に進む。その分岐に C の操作が到達可能なら required。スタブは元に無い名前を「ある」と答えてはならない。
  - 除外する場合(nofollow): 「無い」側の分岐に進み、元と経路が変わる。**「ある」側の分岐に C の操作が到達可能なら nofollow にしてはならない**(required)。保護された import というだけでは nofollow の根拠にならない。
- `P.__version__` の比較・解析: スタブは元と同じ版数文字列を持つこと。

## 4. 到達可能性

- 起点: エントリーモジュールの直下のコードと、import されて実行される全モジュールの直下のコード。
- 関数・メソッドは、呼ばれうるなら到達可能。呼び出し先を特定できない場合(名前だけの一致、値として渡された関数、特殊メソッド、基底クラスからのフック呼び出し)は、候補を全て到達可能とする。
- 次は解析不能として、関係する P を required にする（プロジェクトのコードにある場合。依存ライブラリの中の定数でない import は 10.1 の 3 のとおり warnings に出して前提とする）: 文字列が定数でない動的 import、`eval` / `exec`、エントリーポイント・プラグイン登録、C 拡張からの import や呼び出し。
- 取りこぼしを減らす絞り込み(型の推定など)は、絞った根拠をこの節に追記してから入れる。

## 5. 解析の外にある前提(満たせなければ required)

- P の import そのものに副作用が無い(コーデックやフックの登録、他モジュールへの書き込み)。副作用の有無は P の直下のコードで判定する。
- ビルド時にも P が実行される経路が無い(PyInstaller のフックが依存ライブラリを import する場合、ビルド環境でもスタブが使われる)。該当するフックがあるなら、判定に含めるか、無効化するフックを具体的なファイル名で示す。
- 解析対象の site-packages と、実際にビルドする環境が同じである。版数・パスは解析対象の環境から取る。
- 依存ライブラリの中の、引数が定数でない `import_module` / `__import__` と、対象を特定できない `pkgutil` の列挙が読み込むモジュールは解析の外（warnings に出す。10.1 の 3）。
- site-packages の `.pth` ファイルと `sitecustomize` / `usercustomize` が起動時に実行するコードは解析しない（そこからの import・使用は前提の外）。

## 6. サブモジュールのヒント

- サブモジュール M にも 1〜5 節を同じく適用する(M の外の到達可能なコードが M に対して C の操作をしないこと)。
- 目的は対象パッケージ T(C 拡張)を import 閉包から外すこと。**T に届く経路を全て切る、最小の組**だけを出す。T の排除に寄与しないモジュールは出さない。
- 出す組は互いに重ならず(親と子を同時に出さない)、全部を同時に適用しても 1 節を満たすこと。1 件ずつなら安全、では足りない。
- 組を作れない(T がどこかで C の操作に到達する)ときは、ヒントを出さない。

## 7. 手順(build_instructions)

- 適用 → 復元で、環境が元と同じに戻ること(ファイルと pip の管理情報)。繰り返し適用しても同じ結果になること。
- パスは解析で実際に見つけた場所。site-packages の外や site-packages 自体を消す・上書きする手順は出さない。

## 8. 受け入れ基準

- 2〜6 節・9 節の各行に、**スタブに差し替えて(または除外して)実際に実行する**テストが 1 つ以上ある。
- 実ビルドの基準シナリオ(`C:\tmp\pystub-e2e`)で、証明済みの提案(stubbable / nofollow / submodule_stub_hints)の
  全適用が全シナリオで動作一致する。
- 取りこぼしの基準: asammdf.gui→PySide6 と openpyxl.drawing.image→PIL が、**conditional(9 節)として、
  正しい条件つきで自動で出る**(`conditional_submodule_hints`)。エントリーが条件の機能を使わないシナリオでは、
  証明済み + conditional の全適用で動作一致し、条件を破るエントリーでは 9 節の例外で落ちる。

## 9. 条件付き候補(conditional)

判定を 2 段に分ける。

- **証明済み**(stubbable / nofollow / submodule_stub_hints): 1 節を満たすものだけ。ここは緩めない。
- **条件付き**(analyze の `conditional` / `conditional_submodule_hints`): 安全は示せないが、利用者が特定の機能を
  使わないなら外せるもの。stubbable には絶対に混ぜない。

条件付きに出してよいのは、障害(C の使用に届く経路)が次の「過大近似」か「入力・呼び出し次第の経路」だけのもの:

| 印 | 意味 |
|---|---|
| name | 名前だけの振り分け(受け手の型が分からない `x.m()` を、同名のメソッド全てに届くと仮定) |
| argclass | 引数に渡したクラス(渡した先で生成されると仮定) |
| decorator | 登録デコレータ(飾られた関数が後で呼ばれると仮定) |
| branch | 入力・呼び出し次第の分岐(関数の中の if / except / 条件式・短絡評価の枝、match の case) |

- **確実に実行される**もの(起点 = エントリーと 5 節のビルド時の起点から、上の 4 種以外の辺だけで届くコード単位の、
  分岐の外の使用)は required のまま。上の 4 種以外の辺: import、解決できる呼び出し、`self` / `cls` のメソッド呼び出し、
  解決できる生成とその特殊メソッド、値として渡した関数、解析外の基底のフック、`getattr` の動的な取り出し、
  クラス族、entry_points。ループの本体と try の本体は実行されるものとして扱う(1 回以上回る・例外は起きないとみなす)。
- 入口(確実な集合から最初に出る辺の先)が特定できないものは required(区別できないなら required)。
- 各候補に付けるもの: 推定の削減量(MB。サブモジュールのヒントは排除される対象パッケージの MB)、条件(入口・
  プロジェクトが呼ぶ公開 API からの経路・入口の場所・使用箇所・証明できなかった理由)、確認方法
  (`verify(..., run_entry=True)` の具体的な呼び出し)、`except Exception` で握りつぶされうるかの注記。
- 条件の入口が 10 件を超えるものは上位 10 件と総数を出す。候補は削減量の大きい順。1 MB 未満は既定で省く
  (`include_small_conditional=True` で全件)。
- **条件付き候補のスタブは、踏んだら必ず大きな音で落ちる**: 関数・クラスの呼び出しは
  `PystubConditionalStubError: mcp-pystub のスタブです。<対象> は、次の機能を使わない前提で外されています: <条件>`
  を出す。黙って結果が変わる形(代替値で別の分岐に進む等)は作らない。
  - **既定では握りつぶせない**（第 4 回で変更、10.2 の 3）: 標準エラーに原因を書いて終了コード 70 で即終了する。
    `MCP_PYSTUB_STRICT=0` の時だけ例外（RuntimeError の子クラス）を投げ、その場合は呼び出し元の
    `except Exception` / `except RuntimeError` / `contextlib.suppress` で握りつぶされうる。そうなりうる箇所は
    条件の `may_be_swallowed` / `note` に書く。
- **プロジェクトのコードを調べた証拠と confidence**: 条件の入口ごとに、プロジェクト自身のコード(local 分類の
  ファイル)でのその名前の呼び出し・属性参照の件数(ファイル:行)を付ける。
  - confidence の規則は 10.2.1 で確定した（第 5 回）。high = プロジェクトが入口に届く公開関数を 1 つも呼んでいないという事実の表示（10.5）、
    low = 条件を守れば外せるが、解析したエントリーでも入力によっては終了コード 70 で止まりうる（理由を 1 行で出す）。
- analyze の結果の先頭に `summary`(証明済みの削減見込み MB、conditional(high)の削減見込み MB と件数、
  推奨の一覧(high を上に)、次の手順 `generate_submodule` → `verify(run_entry=True)`)を置く。
- 同じパッケージの中で、パッケージ全体のスタブとサブモジュールのスタブを重ねて適用した場合、内側の手順は
  「親がスタブに置き換えられている」ことを検出して何もしない(7 節: 復元で元のファイルを失わない)。
  検出は「親パッケージの `__init__.py` がバックアップ領域にあるか」で行う。親のディレクトリの有無で判定してはならない
  (サブモジュール単独の適用で、自分のバックアップが作った親ディレクトリを親のスタブと取り違え、元ファイルを退避したまま
  スタブを置かない事故が第 3 回の e2e で起きた。単独適用でスタブが実際に置かれることをテストで確かめる)。
- ImportError の代替(`try: import X / except ImportError: X = None`)の束縛は、元の環境(X がある)では実行されない。
  真偽の判定(`if X:` / `not X`)では、この代替を除いて、種類がクラス・関数・モジュールなら判別(B)として扱う。

## 10. 第 4 回の決定（独立検証 FAIL への対応）

### 10.1 証明済みの段（許可リストのまま、証明できないものは required か conditional）

1. **isinstance / issubclass / except の相手**: 「普通のクラス」と示せた時だけ判別（B）として安全。
   普通のクラス = `metaclass=` などのクラス引数なし、`__instancecheck__` / `__subclasscheck__` / `__subclasshook__`
   なし、クラスのデコレータは `dataclass` / `total_ordering` / `final` / `unique` だけ、基底は `object`・組み込みの型
   （`type` を metaclass とするもの）・同じ条件を満たす解析対象のクラスだけ（Protocol・ABC は基底の時点で外れる。
   ABC の `register` は ABCMeta の時だけあるので、この条件で同時に除かれる）。それ以外は実行（C）として扱う。
2. **有無の判定**（`hasattr(P, "x")`、`try: from P import x / except ImportError`）: x が P で
   **無条件のトップレベルで 1 回だけ束縛**され（`if` / `try` の中・`del`・ImportError の代替でない）、P に
   `globals()[...] = ` / `globals().update(...)` 等が無い時だけ「ある」と扱う。クラスの属性はクラス本体の無条件の
   束縛だけ。サブモジュールの名前は「ある」と扱わない（import の状態で変わる）。それ以外は実行（C）。
3. **pkgutil の列挙**: `pkgutil.iter_modules(X.__path__)` / `walk_packages(X.__path__)` / `iter_modules(__path__)`
   は、X のディレクトリにある全サブモジュール（walk は再帰）を読み込むものとして扱い、それらの関数は
   受け手の分からない属性呼び出し（`mod.go()`）から名前で届くとする。対象を特定できない列挙と、
   **引数が定数でない `import_module` / `__import__` は解決できない**: そのモジュールと行を warnings に出し、
   5 節の前提とする（破れに数えないが、warnings に出ていること）。定数でない import の結果は任意のモジュール
   として扱う（外部の値とはみなさない）。
4. **注釈**: 注釈を実行時に取り出す呼び出し（`typing.get_type_hints`、`inspect.get_annotations`、
   `inspect.signature(eval_str=...)`、`dataclasses.fields` / `asdict` / `astuple`、`attr.fields`、`__annotations__`
   の読み出し）が、注釈のあるモジュールと同じ top-level パッケージかプロジェクトにある（注釈がプロジェクトに
   あるなら、到達可能なコードのどこかにある）場合、その注釈は安全扱いにしない。評価される注釈
   （`from __future__ import annotations` の無いモジュールの、モジュール直下・クラス直下の変数注釈と関数の引数・
   戻り値の注釈）の添字 `X[...]` は、X の実行（`__class_getitem__`）として扱う。
5. **`python -m pkg` 形式**: エントリーが `__init__.py` のあるディレクトリにあり、`__main__.py` か相対 import を
   含むなら、パッケージの外側を起点（sys.path）とし、モジュール名を `pkg.__main__` 等にして相対 import を解決する。
   親パッケージの `__init__.py` はエントリーより先に実行される起点に加える。
6. **import の副作用で別パッケージの属性が変わる**: P の到達済みのモジュール本体が別パッケージ Q のサブモジュール
   Q.y を import し、P の外の到達可能なコードが `hasattr(Q, "y")` で調べる（またはプロジェクトのコードが Q の
   属性を名前の分からない形で調べる）なら、P は required。

### 10.2 条件付きの段

1. **入口の列挙と confidence（第 5 回で確定）**: 使用のあるユニットから、確実でない範囲を辺を逆向きに辿り、
   確実な集合から入る辺を**打ち切らず全て**入口とする（名前での振り分けは全ての呼び出し元を記録しておき補う。振り分け先の
   クラスのインスタンスが確実なコードから作られない辺は入口にしない）。表示は上位 10 件と総数（`conditions_total`）。
   サブモジュールのヒントでは、そのサブモジュール自身の中の入口を「`<サブモジュール>` 以下を import・使用しない」の
   1 件にまとめ、外の入口を使用に近い順に並べる。パッケージ全体の候補は公開 API に近い順。条件 0 件の候補は出さない。
   **high** は次を全て満たすとき。それ以外は **low**（提案は残し、summary にも出す。理由 `confidence_reason` を 1 行で）。
   - a. 列挙が完了している（プロジェクトのコードに、受け手の分からない入口と同名の**呼び出し**が無い。
     `plug.make().run()` のような、呼び出し結果の属性の呼び出しも含む。属性の読み出しは数えない）。
   - b. プロジェクトが入口の関数を呼んでいない（**関数の単位**）。次の場合は「使っている」に数える:
     プロジェクトのコードが入口を解決した参照で指す / 入口が確実に実行される関数の中の入力次第の分岐（私用の補助関数でも、
     確実に実行されるなら同じ。理由には、プロジェクトが呼ぶ公開の関数 `public_api` を出す）/ 入口へ入る呼び出しのある関数を
     プロジェクトが直接呼んでいて、入口から使用まで推定（名前の振り分け等）を挟まずに届く（例: プロジェクトが `MDF.append()`
     を呼び、その中の `self._mdf.append()` から `MDF4.append()` を経て pandas に届く）。
   - c. 入口へ入る辺が、登録・間接呼び出しの仕組みでない: 入れ物（辞書・一覧・集合）に登録するデコレータ
     （解析して `_REG[k] = f` / `xs.append(f)` 等を確かめたもの、または解析できない `X.register` / `app.route` / `bus.on_xxx`
     の形: singledispatch・登録辞書・コールバック一覧）、`operator.methodcaller`、クラス定義時のフック（`__init_subclass__`）。
     確実な経路で実行されると示せるもの（`atexit.register`・登録したモジュールの本体が登録先を呼ぶ）は 2 のとおり required。
   - 根拠: high の候補を適用して、解析したエントリーが止まる・変わる事例を 0 件にする（tests/attacks の c1, c1b, c2, e1, e4, f1〜f3, g_high）。
     low でも、解析したエントリーで変わらないことは `verify(..., run_entry=True)` で確かめられる（next_steps に出す）。
2. **必ず実行されるものは required**: 次は確実な辺として扱う。
   - `atexit.register` で登録された関数（終了時に必ず呼ばれる）
   - 登録デコレータで登録した関数のうち、登録したモジュールの本体が「呼び出し先の分からない呼び出し」
     （ループ変数・添字の呼び出し）をするもの（import 時に登録先を呼び出す）
   - モジュールに無い名前を確実なコードが参照する（`from M import N` を含む）時の `M.__getattr__`
   - 関数の中の `if X is not None:` / `if X:` で、X が ImportError の代替つきで import され、解析対象の環境に実在する
     場合の「ある」側の枝（元の環境では結果が決まる）
   - 実行環境だけで決まる判定（`sys.version_info` / `sys.platform` / `os.name` / `platform.system()` 等）の両方の枝
   - `self.m()` は、呼び出し元のクラスを MRO に含む（インスタンス化された）クラスの `m` へだけ確実な辺。族の外の同名の
     メソッドへは名前の振り分け。
3. **条件違反は既定で必ず止める**: 条件付きスタブは、使われた時点で標準エラーに
   `[mcp-pystub] PystubConditionalStubError: ...` と原因を書き、**終了コード 70 で即終了する**（`except` で
   握りつぶせない）。`MCP_PYSTUB_STRICT=0` の時だけ `PystubConditionalStubError`（RuntimeError の派生）を投げる。
   `may_be_swallowed` は、使用・入口の辺・確実側の呼び出し元から起点までの呼び出しのどれかが、
   `except:` / `except Exception` / `except BaseException` / `except RuntimeError`（タプルも）・
   `contextlib.suppress(...)` の中にある場合に真。
   標準エラーが無い（窓のない exe で `sys.stderr` が None）時は、原因を `pystub_stop.log`（exe のあるフォルダ、
   書けなければ一時フォルダ）に追記する。**制限**（直さない）: 子プロセス（multiprocessing・concurrent.futures・
   subprocess）の中で止まると、親は終了コードや例外として受け取り、親の処理（フォールバック等）が続くことがある。
   `os._exit(70)` は即終了なので、書き込み途中のファイルが残る・`atexit` / `finally` が実行されない。
4. **代わりのオブジェクト `_M`（第 5 回で確定、第 6 回で 10.5 のとおり補正: Enum のメンバー名の一覧・入れ子の `__qualname__`・値の代わりの hash・dunder・関数の docstring）**: 条件付きスタブの `_M` は 2 種類。
   - スタブのクラス（class 文）と、元がクラス・関数・モジュールの名前の代わり: `==`・`!=`・hash・真偽は type の既定
     どおり（PyInstaller のビルド時 import・`typing.Union` の重複除去・辞書の検索のため）。普通のクラスなら str / repr /
     書式も既定どおり（`<class 'mod.Name'>`）。元のクラスが普通のクラスでない（metaclass・Enum 等）なら str / repr /
     書式 / 反復 / 添字は止まる。クラスの属性は、元に無い名前なら止めずに `AttributeError`（`getattr(C, 'x', None)` /
     `hasattr` で機能の有無を試すコードのため）、元にある名前のうち元がクラス・関数なら同じ種類、値なら下の値の代わり。
     クラスの `__doc__` は元の docstring を写す。同じ名前の属性は同じオブジェクトを返す（同一性・hash）。
   - 値の代わり: 呼び出し・添字・真偽・str / repr / 書式・比較・反復・`len`・`in`・演算・数値変換・属性のどれでも止まる。
5. **使用件数**: プロジェクトのコード（到達済みの local ユニット）で、入口を指す**解決した参照**と、受け手の分からない
   同名のメソッド呼び出し（名前の一致で入口に届きうるもの）の場所を数える。字面の一致だけでは数えない。

### 10.3 手順（7 節の追加）

- バックアップは**項目ごとの領域** `<_pystub_bak>/<項目名>/` に置く。領域があること＝その項目が適用中。
- 親の項目が適用中なら、子の項目の適用・配置は何もしない。**子の項目が適用中なら、親の項目の適用は断る**
  （終了コード 1。先に子を復元させる）。同じパッケージに全体とサブモジュールの両方を提案しない（全体が出るなら
  サブモジュールのヒントは出さず、warnings に書く）。
- 元ファイルの移動は「バックアップ側に無く、元の場所にある時だけ」。スタブの撤去は「元ファイルがバックアップ側に
  揃っている時だけ」。これで二重適用・適用の中断・復元の中断のどの時点でも元ファイルを失わない。
- verify_commands は、元がファイルを持つモジュールなら `__file__` が None でない（中身の消えたパッケージが名前空間
  パッケージとして import できてしまうのを検出）ことと、配布物の RECORD の sha256 と実ファイルの一致を確かめる。

### 10.4 資源

- 構文木は全モジュールぶんを同時に持たない。モジュールの木は、ソースの合計 300 KB ぶんまで保持して古いものから
  手放し、必要なら読み直す。関数の本体は、その関数の行だけを読み直して構文解析する（前を空行で埋めて行番号を
  元と同じにする）。歩き終えたユニットの木は持たない。呼び出し側の文字列リテラルの索引は読み込み時に作る。

### 10.5 第 6 回の決定（攻撃の全件は潰さない。保証の拠り所は verify(run_entry=True) と実ビルド）

- **high の規則 b は推移的**: 入口に届く公開関数（`public_api`: プロジェクトが呼ぶ依存ライブラリの関数のうち、確実な辺で
  入口へ入る呼び出しのある関数に届くもの）を、プロジェクトが 1 つでも呼んでいれば low。入口から使用まで推定（名前の振り分け
  等）を挟まずに届く入口に適用する。関数の中で作るメソッドの表（`{'p': o.plot}[k]()`）、`operator.attrgetter` は
  methodcaller と同じ間接呼び出し。`functools.partial(f, 'name')` は f の呼び出し側として名前を伝える。
- **high の意味（第 7 回で書き直し）**: 「プロジェクトから使用まで、推定を挟まずに届く経路が 1 本も無い」という事実の表示
  （止まらないことの保証ではない）。推定 = 名前だけで結び付けた呼び出し・`__del__` のような暗黙の呼び出し・動的な振り分け。
  確定した経路は `route_from_project`、推定の経路は `estimated_routes` に分け、high の候補に確定した経路は出さない。
  推定の経路がある high には「推定の経路があります。verify(run_entry=True) で確かめてください」を付ける。
- **登録の仕組みの判定**: デコレータの中身で、飾る対象を入れ物に入れる（`_REG[k] = f` / `.update({k: f})` /
  `.__setitem__` / `.append` / `setattr(ns, n, f)` / global の再束縛）、インスタンスのメソッドのデコレータ（`@bus.listen`）、
  関数が作ったデコレータを名前に入れたもの（`hook = make()`; `@hook`）。クラスデコレータは、飾るクラスそのものを入れる
  時だけ登録とし（attrs / dataclasses / pydantic 等のクラスを作り替えるライブラリは除く）、そのクラスの本体とメソッドは実行
  されうるとする。基底から継承したメタクラスも定義時に実行されるとする。
- **dunder の有無**: クラスの dunder（`__slots__`・自作の dunder）に対する hasattr / `getattr(C, '__x__', 既定値)` は
  分からないとして実行（C）扱い（証明済みの段では required）。条件付きスタブでは、元のクラスが定義する dunder を読むと止まる。
- **条件付きスタブ**: Enum 等の普通でないクラスにも元の名前（メンバー名）の一覧を持たせ、元にある名前だけ値の代わり、無い名前は
  AttributeError。入れ子のクラスの `__qualname__` は元どおり。値の代わりの hash は止まる（辞書・集合の検索で黙って変わらない）。
  クラスの hash は type の既定。関数・メソッドの docstring も写す。
- **制限（直さない）**: 値の代わりに対する `isinstance` / `type()` / `callable` / `dir()` / `vars()`、スタブのクラスの
  `issubclass` / `__mro__` / `dir()` / `vars()` / `dataclasses.is_dataclass`、外部の基底（NamedTuple 等）から継承した属性、元に無い属性のエラー文は、
  Python の仕組み上スタブ側で止められない（または元と同じにできない）。条件を破った時に限り、止まる前にこれらの結果が元と
  変わりうる。tests/test_attacks.py の LIMITATIONS に名前と期待する結果を挙げている。

### 10.6 第 7 回: verify の実行条件・登録の検出

- verify はエントリーを `sys.argv = [エントリー] + entry_args`、作業フォルダ `cwd`（既定はエントリーのあるフォルダ）で実行し、
  標準出力と終了コード（エントリーと子プロセス全体）を比べる。標準エラー・ファイル出力・import 時に掴まれた stdout は比べない。
  基準（スタブなし）で import が 0 件・エントリーが最後まで走らない・終了コードが 0 でない時は `baseline_failed` を返し、何も通さない。
- 登録の検出を広げる変更（逃げ出す対象・追い切れないデコレータを登録と見なす）と「import 時に登録するパッケージは required」は
  **取り消した**（12 の PySide6・01/08 の pandas・15 の numpy が全て落ちたため）。静的解析の規則は 8c0a487 の状態で凍結し、
  候補を実際に外せるかは動的解析（verify(run_entry=True) と実行の記録）で判定する（README の 3 層の役割）。

## 付録 A. 実装の対応（2 回目の修正で追記）

各節の規則が実装のどこに当たるか。規則を足す・絞るときはここにも追記する。

### 2 節（操作の分類）— 許可リスト方式
- `usage_analyzer._leaf_is_use`: 安全（A/B）とするのは次だけで、それ以外の文脈は全て C（実行）。
  - A: `bind`（一意で無条件の名前への代入の右辺）、`annot`（注釈。`X | None` や `Optional[X]` の中も）、
    `read`（式文としての読み出し）、`hasattr` / `getattr(P, "リテラル")`、`presence`（有無の検出）
  - B: `isinst` / `except`（種類が P のクラスのとき）、`is`（クラス・関数・メソッド・モジュール）
  - 種類が「定数」（無条件のトップレベルで 1 回だけ束縛され、パッケージ内のどこでも書き換えられない
    リテラル）、「stdlib・組み込みの再エクスポート」なら、どの文脈でも安全（スタブが同じ値・同じオブジェクトを持つ）
- 次は全て C: 呼び出し・インスタンス化・継承・デコレータ・演算・比較（`is` 以外）・反復・添字・`with`・
  値として外へ渡す（引数・格納・return・クラス本体の代入）・`del`・未知の式
- 束縛が複数ある名前・条件付きで束縛される名前は、全ての候補（alts）を辿り、どれか 1 つでも C なら C。

### 3 節（判別）
- 例外クラスのスタブは、元の基底を辿って組み込み・stdlib の例外の祖先を継ぐ（`stub_generator._exc_bases`）。
- スタブモジュールの `__getattr__` は、元のモジュールにある名前だけ代替を返し、それ以外は AttributeError。
  dunder 名には答えない（`__all__` 等）。元に無い名前はスタブに出さない。
- 有無の検出: 到達可能なコードの `'X' in sys.modules` / `find_spec("X")` について、P をスタブにすると
  X が読み込まれなくなるなら required。
- nofollow は、実行される import が全て「単純な保護」（try 本体が import だけ、except が pass か、本体で
  束縛した名前への None/False の代入だけ）で、到達可能なコードから P への参照が一切無い場合だけ。

### 4 節（到達可能性）— 起点と、追加した絞り込みの根拠
- 起点: エントリーモジュールの直下と、PyInstaller のフックがあるモジュール（5 節）。
- 関数は到達したものだけコード単位を作る。呼び出し先を特定できない呼び出しは、名前の一致する
  （インスタンス化されうるクラスの）メソッドを全て到達とする。インスタンス化されたクラスの特殊メソッド・
  property、解析外の基底（stdlib 等）が名前で呼びうるメソッド、`__init_subclass__` を持つ基底の子クラス、
  `cls()` / `type(self)()` / `__subclasses__()` のクラス族、登録デコレータ（引数を保持・登録するもの）で
  飾られた関数は到達とする。
- 解析不能で required にするもの: プロジェクトのコードにある非定数の動的 import・`exec` / `eval`（非定数）・
  `sys.modules[非定数]`、`entry_points()` で読み込まれるプラグインのパッケージ。
- **絞り込み（根拠）**:
  1. `getattr(obj, 名前)` の名前が文字列リテラル、囲むクラスのクラス定数、モジュールの定数に解決できる
     ときは、その名前だけ（定数伝播。元でも同じ名前しか取り出されない）。
  2. `getattr(obj, 引数)` の引数が代入し直されない関数の引数で、全ての呼び出し側がリテラルを渡すときは、
     その集合だけ（呼び出し側の定数伝播。1 つでも非リテラルなら全て）。
  3. `if 'X' not in sys.modules: return/raise` の後の文は、X が他の到達可能なコードで読み込まれる場合だけ
     実行される（X が読み込まれなければ、元でもその後は実行されない）。
  4. 受け手が組み込み・stdlib の値（リテラル、stdlib の呼び出し結果など）の属性呼び出しは、名前による
     振り分けの対象にしない（解析対象のメソッドが呼ばれることは無い）。
  5. `Base[T]`（Generic 等の添字つき基底）は `Base` として扱う（添字は基底の種類を変えない）。
  6. `entry_points(group=...)` の群は定数伝播で求め、その群のプラグインだけ読み込む。群が分からない呼び出しは
     コマンド用の群（console_scripts 等）以外の全群。呼び出し元が P 自身なら、P をスタブにすれば呼ばれない。
  7. ライブラリの中の非定数の動的 import は、そのライブラリ自身（または定数の接頭辞が示す範囲）の
     グラフ上のモジュールを全て読み込むものとみなす（遅延ローダーの慣用）。

### 5 節（解析の外にある前提）
- PyInstaller のフック（`PyInstaller/hooks`、`_pyinstaller_hooks_contrib`、パッケージ同梱の `__pyinstaller`）
  があるモジュールで、静的な import グラフに入っているものは、ビルド時に実行されうる起点として扱う
  （`usage_analyzer.find_pyinstaller_hooks`）。そのモジュールの import 時の使用は required の根拠になる。
- C 拡張のバイナリに `\0名前\0` / `\0名前.` があるパッケージは required（C 拡張からの import）。

### 6 節（サブモジュールのヒント）
- `usage_analyzer.find_submodule_hints`: 静的な import グラフで T を import する全モジュールについて、
  外の到達可能なコードが C の操作をしない最短の祖先サブモジュールを選び、全部を同時に適用して
  (a) 組の外からの使用が無い (b) T が静的なグラフの閉包から消える、を確かめる。満たさなければ出さない。

### 7 節（手順）
- バックアップは site-packages の外（`<site-packages の親>/_pystub_bak`）。既にあれば移動しない。
  スタブは置き直す。復元後は空になったバックアップ領域を消す。pip uninstall はしない。
- 名前空間を共有するパッケージは、RECORD でファイルの持ち主の配布物を全て求め、方法 2 で全て入れ直す。
- `.pth` で sys.path に足されたディレクトリ（pywin32 の win32 等）ではなく、本当の site-packages を基準にする。

### 動的検証（verify ツール）
- 静的解析は候補を出すだけ。`verify` は対象環境の python を子プロセスで起動し、スタブを meta path finder で
  差し込んで、import グラフ上のモジュールを import する（site-packages は書き換えない）。スタブ無しの基準と
  比べて新たに失敗したものの原因を外し、通った組を返す。静的判定の穴を verify に任せることはしない。
