# スタブ可否の判定仕様(草案)

判定ロジックとテストはこの文書を基準にする。実装の都合で決めた規則は、ここのどの項に当たるかを示せること。

## 1. 守るべき性質

パッケージ P をスタブ S に置き換えた(または除外した)プログラムが、**エントリーポイントから到達しうる全ての実行で、元と同じ観測結果(出力・戻り値・例外・ファイル)になる**こと。

- 「stubbable / nofollow / サブモジュールのヒント」を出してよいのは、この性質を静的に示せたときだけ。
- 示せないとき(解析不能・判断に迷う)は required。
- 逆方向(示せるのに required)は安全だが削減の取りこぼしであり、不具合として数える。

## 2. 操作の分類

P 由来のオブジェクトに対する操作を 3 種に分ける。

| 分類 | 操作 | 扱い |
|---|---|---|
| A. 束縛 | `import P`、`from P import x`、`P.x` の読み出し、別名への代入、型注釈 | スタブが同じ名前を同じ種類(クラス / 関数 / 定数 / サブモジュール)で提供すれば安全 |
| B. 判別 | `isinstance(v, P.C)`、`issubclass`、`except P.Err`、`v is P.X`、`hasattr(P, "x")`、`P is None` | 結果が元と同じになる場合に限り安全。下の 3 節 |
| C. 実行 | 呼び出し、インスタンス化、継承、デコレータ適用、演算、反復、`with`、値として外へ渡す | P の実装が要る。到達可能なら required |

定義時に評価されるもの(既定引数、デコレータ、クラス本体、モジュール直下の式)は、その定義が置かれた場所の実行として数える。

## 3. 判別(B)が安全な条件

- `isinstance(v, P.C)` / `except P.Err`: P の実体がどこでも生成されない(C の到達可能な実行が無い)なら、元でもスタブでも結果は偽で一致する。スタブの C はクラス、Err は元と同じ基底(`Exception` 等)を継ぐこと。
- **有無の検出**(`try: import P / except ImportError`、`hasattr`、`P is None`、`find_spec("P")`): 元の環境では P が「ある」。
  - スタブに置き換える場合: 「ある」側の分岐に進む。その分岐に C の操作が到達可能なら required。スタブは元に無い名前を「ある」と答えてはならない。
  - 除外する場合(nofollow): 「無い」側の分岐に進み、元と経路が変わる。**「ある」側の分岐に C の操作が到達可能なら nofollow にしてはならない**(required)。保護された import というだけでは nofollow の根拠にならない。
- `P.__version__` の比較・解析: スタブは元と同じ版数文字列を持つこと。

## 4. 到達可能性

- 起点: エントリーモジュールの直下のコードと、import されて実行される全モジュールの直下のコード。
- 関数・メソッドは、呼ばれうるなら到達可能。呼び出し先を特定できない場合(名前だけの一致、値として渡された関数、特殊メソッド、基底クラスからのフック呼び出し)は、候補を全て到達可能とする。
- 次は解析不能として、関係する P を required にする: 文字列が定数でない動的 import、`eval` / `exec`、エントリーポイント・プラグイン登録、C 拡張からの import や呼び出し。
- 取りこぼしを減らす絞り込み(型の推定など)は、絞った根拠をこの節に追記してから入れる。

## 5. 解析の外にある前提(満たせなければ required)

- P の import そのものに副作用が無い(コーデックやフックの登録、他モジュールへの書き込み)。副作用の有無は P の直下のコードで判定する。
- ビルド時にも P が実行される経路が無い(PyInstaller のフックが依存ライブラリを import する場合、ビルド環境でもスタブが使われる)。該当するフックがあるなら、判定に含めるか、無効化するフックを具体的なファイル名で示す。
- 解析対象の site-packages と、実際にビルドする環境が同じである。版数・パスは解析対象の環境から取る。

## 6. サブモジュールのヒント

- サブモジュール M にも 1〜5 節を同じく適用する(M の外の到達可能なコードが M に対して C の操作をしないこと)。
- 目的は対象パッケージ T(C 拡張)を import 閉包から外すこと。**T に届く経路を全て切る、最小の組**だけを出す。T の排除に寄与しないモジュールは出さない。
- 出す組は互いに重ならず(親と子を同時に出さない)、全部を同時に適用しても 1 節を満たすこと。1 件ずつなら安全、では足りない。
- 組を作れない(T がどこかで C の操作に到達する)ときは、ヒントを出さない。

## 7. 手順(build_instructions)

- 適用 → 復元で、環境が元と同じに戻ること(ファイルと pip の管理情報)。繰り返し適用しても同じ結果になること。
- パスは解析で実際に見つけた場所。site-packages の外や site-packages 自体を消す・上書きする手順は出さない。

## 8. 受け入れ基準

- 2〜6 節の各行に、**スタブに差し替えて(または除外して)実際に実行する**テストが 1 つ以上ある。
- 実ビルドの基準シナリオ(`C:\tmp\pystub-e2e`)で、提案の全適用が全シナリオで動作一致する。
- 取りこぼしの基準: asammdf の PySide6 排除、openpyxl の PIL 排除が、自動提案だけで出る。

## 付録 A. 実装の対応（2 回目の修正で追記）

各節の規則が実装のどこに当たるか。規則を足す・絞るときはここにも追記する。

### 2 節（操作の分類）— 許可リスト方式
- `usage_analyzer._leaf_is_use`: 安全（A/B）とするのは次だけで、それ以外の文脈は全て C（実行）。
  - A: `bind`（一意で無条件の名前への代入の右辺）、`annot`（注釈。`X | None` や `Optional[X]` の中も）、
    `read`（式文としての読み出し）、`hasattr` / `getattr(P, "リテラル")`、`presence`（有無の検出）
  - B: `isinst` / `except`（種類が P のクラスのとき）、`is`（クラス・関数・メソッド・モジュール）
  - 種類が「定数」（無条件のトップレベルで 1 回だけ束縛され、パッケージ内のどこでも書き換えられない
    リテラル）、「stdlib・組み込みの再エクスポート」なら、どの文脈でも安全（スタブが同じ値・同じオブジェクトを持つ）
- 次は全て C: 呼び出し・インスタンス化・継承・デコレータ・演算・比較（`is` 以外）・反復・添字・`with`・
  値として外へ渡す（引数・格納・return・クラス本体の代入）・`del`・未知の式
- 束縛が複数ある名前・条件付きで束縛される名前は、全ての候補（alts）を辿り、どれか 1 つでも C なら C。

### 3 節（判別）
- 例外クラスのスタブは、元の基底を辿って組み込み・stdlib の例外の祖先を継ぐ（`stub_generator._exc_bases`）。
- スタブモジュールの `__getattr__` は、元のモジュールにある名前だけ代替を返し、それ以外は AttributeError。
  dunder 名には答えない（`__all__` 等）。元に無い名前はスタブに出さない。
- 有無の検出: 到達可能なコードの `'X' in sys.modules` / `find_spec("X")` について、P をスタブにすると
  X が読み込まれなくなるなら required。
- nofollow は、実行される import が全て「単純な保護」（try 本体が import だけ、except が pass か、本体で
  束縛した名前への None/False の代入だけ）で、到達可能なコードから P への参照が一切無い場合だけ。

### 4 節（到達可能性）— 起点と、追加した絞り込みの根拠
- 起点: エントリーモジュールの直下と、PyInstaller のフックがあるモジュール（5 節）。
- 関数は到達したものだけコード単位を作る。呼び出し先を特定できない呼び出しは、名前の一致する
  （インスタンス化されうるクラスの）メソッドを全て到達とする。インスタンス化されたクラスの特殊メソッド・
  property、解析外の基底（stdlib 等）が名前で呼びうるメソッド、`__init_subclass__` を持つ基底の子クラス、
  `cls()` / `type(self)()` / `__subclasses__()` のクラス族、登録デコレータ（引数を保持・登録するもの）で
  飾られた関数は到達とする。
- 解析不能で required にするもの: プロジェクトのコードにある非定数の動的 import・`exec` / `eval`（非定数）・
  `sys.modules[非定数]`、`entry_points()` で読み込まれるプラグインのパッケージ。
- **絞り込み（根拠）**:
  1. `getattr(obj, 名前)` の名前が文字列リテラル、囲むクラスのクラス定数、モジュールの定数に解決できる
     ときは、その名前だけ（定数伝播。元でも同じ名前しか取り出されない）。
  2. `getattr(obj, 引数)` の引数が代入し直されない関数の引数で、全ての呼び出し側がリテラルを渡すときは、
     その集合だけ（呼び出し側の定数伝播。1 つでも非リテラルなら全て）。
  3. `if 'X' not in sys.modules: return/raise` の後の文は、X が他の到達可能なコードで読み込まれる場合だけ
     実行される（X が読み込まれなければ、元でもその後は実行されない）。
  4. 受け手が組み込み・stdlib の値（リテラル、stdlib の呼び出し結果など）の属性呼び出しは、名前による
     振り分けの対象にしない（解析対象のメソッドが呼ばれることは無い）。
  5. `Base[T]`（Generic 等の添字つき基底）は `Base` として扱う（添字は基底の種類を変えない）。
  6. `entry_points(group=...)` の群は定数伝播で求め、その群のプラグインだけ読み込む。群が分からない呼び出しは
     コマンド用の群（console_scripts 等）以外の全群。呼び出し元が P 自身なら、P をスタブにすれば呼ばれない。
  7. ライブラリの中の非定数の動的 import は、そのライブラリ自身（または定数の接頭辞が示す範囲）の
     グラフ上のモジュールを全て読み込むものとみなす（遅延ローダーの慣用）。

### 5 節（解析の外にある前提）
- PyInstaller のフック（`PyInstaller/hooks`、`_pyinstaller_hooks_contrib`、パッケージ同梱の `__pyinstaller`）
  があるモジュールで、静的な import グラフに入っているものは、ビルド時に実行されうる起点として扱う
  （`usage_analyzer.find_pyinstaller_hooks`）。そのモジュールの import 時の使用は required の根拠になる。
- C 拡張のバイナリに `\0名前\0` / `\0名前.` があるパッケージは required（C 拡張からの import）。

### 6 節（サブモジュールのヒント）
- `usage_analyzer.find_submodule_hints`: 静的な import グラフで T を import する全モジュールについて、
  外の到達可能なコードが C の操作をしない最短の祖先サブモジュールを選び、全部を同時に適用して
  (a) 組の外からの使用が無い (b) T が静的なグラフの閉包から消える、を確かめる。満たさなければ出さない。

### 7 節（手順）
- バックアップは site-packages の外（`<site-packages の親>/_pystub_bak`）。既にあれば移動しない。
  スタブは置き直す。復元後は空になったバックアップ領域を消す。pip uninstall はしない。
- 名前空間を共有するパッケージは、RECORD でファイルの持ち主の配布物を全て求め、方法 2 で全て入れ直す。
- `.pth` で sys.path に足されたディレクトリ（pywin32 の win32 等）ではなく、本当の site-packages を基準にする。

### 動的検証（verify ツール）
- 静的解析は候補を出すだけ。`verify` は対象環境の python を子プロセスで起動し、スタブを meta path finder で
  差し込んで、import グラフ上のモジュールを import する（site-packages は書き換えない）。スタブ無しの基準と
  比べて新たに失敗したものの原因を外し、通った組を返す。静的判定の穴を verify に任せることはしない。
